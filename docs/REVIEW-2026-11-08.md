# RegLens design and code review — 8 November 2026

Review scope: local open-source MVP; regulatory Q&A is primary, synthetic policy gap analysis secondary. This is an engineering and product review, not a legal validation of the regulatory answers. No application fixes were made.

## 1. Baseline and documentation

Read README, DESIGN, ROADMAP, project rules, dependency manifests, and selected implementation and test files along the main flows. No CodeGraph index exists, so ordinary file inspection was used.

Implemented architecture substantially matches the description: official-source ingestion → structural chunks → Postgres full-text/vector retrieval → reranking → single-pass or agent answering → deterministic checks → CLI/Streamlit/FastAPI/Next.js. The agent has separate CLI/MCP and Messages API runtimes. Gap analysis extracts an obligation register and matches batches against the whole synthetic policy.

Documentation drift is material: ROADMAP's status summary still says phase 4 is not started, despite its completed implementation later in the same document. DESIGN lists Next.js as unbuilt after describing its implementation, and its usage totals differ from README. Reconcile these before launch and attach dates and evaluation versions to claims.

## 2. Architecture assessment

Good choices for this scope: one database; deterministic hierarchy prefixes; read-only domain tools; local retrieval models; provider separation; explicit partial answers; existing offline tests; visible traces. These choices support a reviewable portfolio project without unnecessary infrastructure.

The main weakness is that evidence provenance is not enforced end to end. Model-produced prose, model-produced claim lists, database-resolved citations, and user-facing verification status can disagree. A validated answer object should be the shared boundary for all renderers. It should preserve the exact passages supplied to the model, distinguish mechanical checks from semantic support, and represent malformed or incomplete results explicitly.

Routing logic is duplicated in runtime and evaluation. Share an orchestration function or a route execution plan to prevent differences in fallback handling, retrieval gates, and token accounting. Keep the two agent transports but give them the same provenance and result-validation contract.

## 3. Prioritised findings

P1 = address before presenting the relevant trust guarantee publicly. P2 = substantive correctness/reliability issue. P3 = polish. These priorities reflect the local MVP, not an assumed hosted service.

### F1 — P1: Agent citations are accepted without proof the model received their text

Evidence: `src/reglens/agent/run.py:128–139`, `:303–304`; `src/reglens/agent/tools.py:114–119`.

`_lookup` first resolves a key against the entire database. The received-key list is used only to recover shortened keys, not to authorise citations. A model can name a real provision it never read and have it become ordinary context with a passing citation check. Also, trace keys from `follow_reference` include target references without their text, so mere membership in the current trace list would not be sufficient.

Offline reproduction: mock the database resolver to return one existing row, call `_resolve(None, ['CRR Art. 1'], [])`; the result maps it to `C1` despite an empty received list.

Fix: preserve actual tool-returned content and chunk/window IDs; distinguish reference pointers from read passages. Resolve final citations only against text actually delivered, with explicit handling for truncated passages. Test unseen existing keys, reference-only targets, snippets, and windowed text.

### F2 — P1: The UI overstates what the citation checker establishes

Evidence: `src/reglens/answer/verify.py:55–88`; `web/src/components/ask/answer-view.tsx:153`; `src/reglens/ui/app.py:110`.

The checker establishes citation existence, numeric overlap, and a limited legal-level rule. It does not check semantic entailment, negation, units, conditions, or whether the prose is faithfully represented in the separate claim list. The UI says claims are “supported by their sources.”

Offline reproduction: source “The institution must validate annually.” with claim “Validation is optional.”, citation C1, kind law → `ok=1`, `supported_rate=1.0`. This is a limitation of a deliberately mechanical checker; the defect is presenting it as stronger assurance.

Fix: label this “mechanical citation checks passed,” state the limits adjacent to it, and evaluate semantic support separately. Validate the relationship between displayed prose and claims. Do not equate the 0.99 mechanical pass rate with citation accuracy.

### F3 — P1: Obligation extraction can reuse stale results after source text changes

Evidence: `src/reglens/gap/register.py:150–151`, `:219–220`.

Extraction cache identity hashes chunk IDs only. A source correction or version update can keep the same structural IDs but change regulatory text. The old extraction is then reused and attached to the current passages; quote checking cannot establish that all current obligations were extracted.

Offline reproduction: two Passage instances with identical chunk IDs and different text produce identical `batch_id` values.

Fix: hash full input text and relevant metadata, extraction prompt, and model/settings. Record source fingerprints in the output register. Test a source update with stable IDs.

### F4 — P2: Evaluation caches can report stale answers and grades

Evidence: `src/reglens/eval/answers.py:29–45`, `:98–100`; `src/reglens/eval/judge.py:83–90`.

Single-pass answers are keyed by system prompt and item ID. Question edits, model/config changes, retrieval changes, and corpus updates do not invalidate them. Agent hashing covers some code but omits API-loop code and other relevant inputs. Judge cache validation checks the reference answer but not the candidate answer. Regenerating an answer in the same namespace can therefore preserve its old grade.

Fix: use a manifest/fingerprint of question, corpus/index version, relevant retrieval/tool/prompt code, model, and settings. Judge identity must include question, candidate answer, reference, and judge settings. Preserve historical run manifests rather than silently mixing generations. Re-establish benchmark results from correctly identified artifacts before claiming reproducibility.

### F5 — P2: Stop disconnects the browser but does not cancel server work

Evidence: `web/src/components/ask/ask-view.tsx` Stop handler; `src/reglens/api/app.py:190–218`.

The frontend aborts fetch. The backend worker is a detached thread with no cancellation event, and provider/tool execution has no disconnect signal. Work and model spending can continue after Stop, and another submission can overlap it. The stream iterator also has no explicit disconnect-aware termination while waiting for worker events.

Fix: propagate cancellation through orchestration, check between tools/model calls, close active provider requests where supported, and bound worker concurrency. Explain any in-flight request that cannot be cancelled. Test disconnect during a blocked fake provider and verify that no subsequent calls occur.

### F6 — P2: Gap verdict validation accepts missing evidence and invents a status

Evidence: `src/reglens/gap/match.py:105–125`.

`ok = not quote or ...` treats empty evidence as verified for all statuses. Unknown clause IDs are discarded, and invalid status values are converted to `missing`. This can turn malformed output into a substantive finding or accept unsupported coverage.

Offline reproduction: reply with only `{id: 'OB-1', status: 'covered'}` produces `covered`, no clauses, empty quote, `quote_ok=True`.

Fix: require valid clause references and nonempty matching evidence for statuses that depend on policy content. Represent invalid output as unassessed/error; do not convert invalid status to missing. Keep missing-evidence semantics separate from quote verification.

### F7 — P2: Gap analysis silently serves the committed demo ahead of local results

Evidence: `src/reglens/gap/evaluate.py:30–36`; `src/reglens/api/app.py:222–231`.

`latest_result` always prefers `coverage-demo.json`, which exists in this checkout. A newly generated local analysis cannot appear through this API or its exports. The UI identifies the file, but there is no run selector and the API description promises the saved run.

Fix: make demo selection explicit, allow a run identifier, or prefer local runs with a clearly labelled demo fallback. Test both files existing together.

### F8 — P2: Agent token threshold is a soft stop rather than a hard cap

Evidence: `src/reglens/agent/api_loop.py:158–194`.

The threshold is checked after a completed call and after tools have executed. Once reached, the loop still makes another model call to request a final answer; a model that keeps calling tools can continue receiving stop results until the turn cap. A final non-tool response returns before threshold handling. Thus the documented hard per-question token limit is not enforced; max turns is the actual hard boundary.

Fix: describe the current limit as a soft threshold or enforce admission before each request, reserve a final-response allowance, and reject further calls once exhausted. Include routing/fallback usage in any budget advertised as per-question. Test repeated tool requests after threshold exhaustion.

### F9 — P2: Partial gap evaluations can display inflated recall

Evidence: `src/reglens/gap/evaluate.py:48–58`; `web/src/components/gap/gap-view.tsx` planted-gap summary.

Recall divides by gaps with at least one linked verdict, excluding gaps with no returned obligations. A limited or incomplete run can therefore report 100% despite not evaluating all planted gaps; the UI describes that percentage as covering `data.gaps` deficiencies. The existing full 15-gap result is not shown to be affected.

Fix: report total-gap recall and assessed coverage separately; mark partial evaluations incomplete. Keep conditional recall only if explicitly labelled.

### F10 — P2: Malformed model output can bypass the structured result contract

Evidence: `src/reglens/answer/pipeline.py:184–199`; `src/reglens/agent/run.py:292–300`; `web/src/components/ask/answer-view.tsx:85–106`.

On JSON parse failure, raw model output becomes the displayed answer with no claims. The answer view only presents errors when answer text is empty, so this path hides the parsing warning and omits checks. Parsed JSON also lacks strict schema validation. An apparently ordinary answer can therefore be shown without the structured grounding metadata promised by the interface.

Fix: validate with a typed response schema and fail visibly or retry under a bounded policy. If raw output is useful diagnostically, put it behind an explicit unverified-output state. Test malformed JSON and structurally invalid but parseable replies.

## 4. Security and operational assessment

In the inspected code, keys are held in React state and passed per request through the local backend to the SDK; no explicit key persistence was found. UI/README wording that keys go “only” to Anthropic omits the backend hop; web/README describes this more accurately. Align the wording, especially for configurable remote API URLs.

Inspected SQL uses parameter binding for user-derived values, and the CLI provider uses a subprocess argument list rather than shell interpolation. These are useful safeguards, not a full security audit. CORS and loopback defaults suit local use; they are not authentication for a future hosted subscription endpoint.

The law download URL starts with HTTP (`src/reglens/ingest/download.py:25`), and lock checksums are recorded from received bytes rather than independently authenticated content. Prefer an HTTPS entry point and verify redirects remain HTTPS. Existing downloaded-file reuse does not recheck its hash. These are provenance-hardening recommendations; no network interception or corrupted corpus was demonstrated.

Source text and policy content are included in model prompts, so instruction/data separation and injection resistance deserve explicit adversarial tests. No exploit was demonstrated. Exact current model availability, provider beta compatibility, external source freshness, and reuse terms were not independently verified in this review.

## 5. Product and visual review

Started the production frontend and API locally with model warmup disabled. Inspected the Ask and gap pages in a desktop browser, including the API-unavailable state before starting the backend. Did not submit a paid or subscription question.

The desktop layout is restrained and readable: clear question entry, example prompts, distinct quick/deep modes, visible disclaimer, status counts, and expandable evidence. The gap page accurately labels its policy synthetic and its output a reviewer's starting point.

Recommended changes:

- Put the tuned-on-the-same-policy caveat and the small-sample precision limitation next to the prominent 100% planted-gap result. They are currently explained in the results document, not alongside the UI metric.
- Offer direct official-source URLs and source version metadata from citation panels. Current panels expose extracted corpus text, which makes comparison with official texts harder.
- Make verification failures, partial answers, malformed results, and cancellation semantics explicit before adding visual polish.
- Expose institution applicability consistently. The current UI deliberately limits the SI/LSI selector to Quick; Auto/Deep and their tools have no equivalent filter, although applicability matters to all modes. This is a capability gap, not a hidden UI filter bug.
- Implement standard radio-group arrow-key behaviour and an accessible group name for custom segmented controls. Add `aria-expanded` to source disclosure buttons and a persistent accessible label to gap search. Provide an actionable retry for API-unavailable metadata.
- Add an obvious empty-filter result and make unassessed rows selectable when present. Current status cards omit unassessed.

Mobile, dark mode, screen-reader operation, live answer/citation interaction, and keyboard-only end-to-end behaviour were not browser-verified. The accessibility comments above are based on component source and observed accessibility state, not a claim of a full accessibility audit.

## 6. Evaluation assessment

Read the harder-question and gap-analysis reports and inspected answer/judge/gap evaluation code. Existing evidence supports a promising benchmark on a practitioner-reviewed, LLM-assisted development set. It does not establish production error rates or legal correctness on arbitrary questions.

The gap report candidly states that 15/15 was achieved after prompt changes on the same planted gaps and that only approximately 11/20 sampled findings belong in a validation policy. Keep those qualifications wherever the result is showcased. Run the planned untouched second policy and an independently labelled precision sample before broader claims.

Prioritise a frozen holdout, semantic citation support and completeness, applicability, temporal scope, unsupported prose, near-miss abstentions, and parity between CLI/MCP and API runtimes. Publish run manifests and uncertainty rather than interpreting “zero wrong” on this set as a guarantee. No paid benchmark was rerun, and published numerical scores were not independently reproduced from fresh model calls.

5. Reconcile docs, improve source navigation and accessibility, then run the untouched evaluation sets and a full responsive/browser answer walkthrough.

Passing offline tests and build checks does not close these gaps. Application source remains unchanged; this report is the review artifact.
